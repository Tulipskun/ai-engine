# ข้อกำหนดด้านการทำงาน

REQ-001 — Harness รับ canonical input ได้โดยไม่ขึ้นกับ transport

REQ-002 — CLI และ Discord สามารถใช้ Harness/Agent runtime เดียวกันได้

REQ-003 — แต่ละ session มี state แบบถาวรที่แยกจากกัน และสามารถกู้คืนได้หลัง process restart

REQ-004 — Agent สามารถทำลูป model → tool call → tool result → model จนกว่าจะไม่มี tool call เหลือ

REQ-005 — ความล้มเหลวของ tool ต้องถูกส่งกลับมาในรูปแบบ tool result เพื่อให้ Agent สามารถกู้คืนได้โดยไม่ทำให้ทั้ง turn ล้มเหลว

REQ-006 — รูปแบบ request/response เฉพาะของ provider ต้องถูกแยกไว้หลัง adapter และแปลงผ่าน canonical SDK model

REQ-007 — การค้นหา provider model ต้องใช้ catalogue ของ provider ที่ดึงจากระบบจริง และเมื่อ refresh สำเร็จต้องแทนที่ข้อมูล catalogue เดิมที่ค้างอยู่

REQ-008 — การ retry ต้องใช้ API key ของ session ที่เลือกไว้ และห้ามเปลี่ยน key โดยอัตโนมัติ

REQ-009 — output แบบ streaming จะต้องไม่ถูก replay โดยอัตโนมัติหลังจากเริ่มส่ง output แล้ว

REQ-010 — **ยกเลิก (CHANGE-087)**: browser automation ถูกลบออกทั้งหมด (Go CDP client, BiDi/pipe modes, `config/browser.json`, `config:browser`, 13 `browser_*` tools) การทำงานที่ต้องใช้เบราว์เซอร์ต้องทำผ่าน `bash` (headless CLI, curl) — ข้อกำหนดเดิม: เดิมระบุว่า browser automation ต้องใช้ Go CDP implementation ที่อยู่ในตัว โดยไม่ใช้ Playwright หรือ Node.js worker

REQ-011 — Runtime configuration ต้องเป็นแบบไฟล์ภายใต้ layout `~/.local/share/ai` ที่กำหนดไว้ และไม่ต้องใช้ environment variable ในการตั้งค่า — **ยกเลิก/แทนที่: entry.json เดินมีแค่ discord/cli; ตอนนี้ mobile เท่านั้น (CHANGE-059)**

REQ-012 — Project requirements ต้องเก็บอยู่ใน repository และถือเป็น source of truth สำหรับงานของโปรเจค

REQ-013 — ก่อน implement request ใหม่ AI ต้องตรวจสอบ repository requirements และบันทึก specification change ที่ request นั้นทำให้เกิดขึ้น

REQ-014 — เมื่อสร้าง software project ใหม่ AI ต้องสร้างและเติมข้อมูลใน `requirements/` ของ project นั้นก่อนเริ่ม implementation ในส่วนสำคัญ

REQ-015 — การเปลี่ยนแปลงโค้ดต้องรักษาความรับผิดชอบของแต่ละ module ให้ชัดเจน และต้องเพิ่มหรือแก้ functionality ใน module ที่รับผิดชอบโดยตรง เว้นแต่มีการเปลี่ยน architecture ที่บันทึกไว้อย่างชัดเจน

REQ-016 — เมื่อเปิด planning, Main Agent จะได้รับ planning tools, tools สำหรับ orchestration ของ sub-agent และ read-only context tool เดียวคือ `read` เท่านั้น (CHANGE-087) ไม่ใช่เนื้อหาไฟล์ และต้องปฏิเสธ write/exec call โดยตรง (bash ถูกซ่อนจาก Definitions และถูกปฏิเสธโดย Execute) รวมถึงหลังจากบันทึกแผนแล้วด้วย ผลลัพธ์ของ orchestration tools ยังคงเป็น evidence-only — Main Agent ห้ามได้รับ byte stream, base64, MIME data หรือเนื้อหาไฟล์ผ่าน tool result ของ orchestration Main Agent ไม่มี tool ไหนนอกจาก `read` จึงค้นหา path เองไม่ได้ `index.md` คือแผนที่ของโปรเจกต์: ต้องอ่าน `index.md` ก่อนเสมอ แล้วอ่านเฉพาะไฟล์ที่มันระบุว่าเกี่ยวข้อง (ไม่เกิน ~10 calls ต่อรอบ, ห้ามอ่านซ้ำไฟล์เดิม) แล้วเขียน delegation contract สั่ง worker (CHANGE-054) โดยความพยายามต้องได้สัดส่วนกับความซับซ้อนของงาน: งานที่ต้องใช้ repository context ให้ Main อ่านเองใน main context ก่อน — งานคิด/ออกแบบ/ตัดสินใจทำใน main context เสมอ (serial on thinking) delegate เฉพาะงาน execute ที่มีขอบเขตชัด หรืองาน lookup แบบ read-only ที่ขนานกันได้ (CHANGE-054) งานเล็กน้อยที่ไม่ต้องใช้ repository context (เช่น สร้าง/ลบไฟล์เดียว) ต้องใช้แผนขั้นเดียวที่สั้นที่สุดโดยข้าม investigation แยก และแผนทุกขนาดต้องมีจำนวน step น้อยที่สุดที่ครอบคลุมเป้าหมาย และทุก turn ของ Main Agent เมื่อมีแผนอยู่แล้ว system prompt ต้องแนบ checklist ปัจจุบัน (ลำดับ step พร้อมสถานะ pending/ready/running/awaiting_review/failed/completed) เพื่อให้ Main Agent เป็นผู้ถือภาพรวมและตรวจรายการด้วยตนเอง (CHANGE-022) ข้อความที่ไม่ใช่งาน (ทักทาย/ขอบคุณ/acknowledgement/คำถามที่ตอบได้ตรงจากบทสนทนาโดยไม่ใช้ tools, repository context หรืองานที่ต้องทำ) ให้ Main Agent ตอบตรงทันทีโดยไม่สร้างแผน ไม่ delegate และไม่ investigate (CHANGE-032)

REQ-017 — เมื่อ `DisablePlanning: true`, execution/worker agent ต้องคง system prompt และ execution tool definitions ที่ได้รับมาไว้ทั้งใน turn ปกติและ streaming turn รวมถึงตอนทำต่อหลัง tool result; Harness ห้ามแทรกข้อจำกัดของ Main Agent หรือ planning/delegation tools เข้าไป ค่าเริ่มต้นของคำสั่ง sub-agent ต้องจำกัดงานให้อยู่ใน scope ที่ได้รับ ห้าม delegation ต่อ และห้ามสื่อสารกับ end user โดยตรง และต้องรายงานสิ่งที่ตรวจพบ/ผลลัพธ์ให้ planner การตรวจสอบผลต้องใช้วิธีที่น้อยที่สุดแต่เพียงพอ: คำสั่งเดียวที่พิสูจน์ผลลัพธ์ได้ (หรือ shell line เดียวที่รวมการตรวจที่เกี่ยวข้อง) ห้ามทำซ้ำรายการที่เทียบเท่ากัน (เช่น ls/wc/cat/stat ไฟล์เดียวกัน) เมื่อพิสูจน์ผลได้แล้ว และห้ามลองสูตรคำสั่งแบบอื่นต่อหลังจากการตรวจสำเร็จแล้ว ภาษาที่ใช้ระหว่าง planner↔worker (ทั้ง task ที่สั่งและรายงานที่ส่งกลับ) ต้องเป็นภาษาอังกฤษเสมอเพื่อลด token ไม่ว่าจะพูดภาษาใดกับผู้ใช้ (CHANGE-024)

REQ-018 — การประกอบ role prompt ต้องรักษา repository requirements และ custom context ไว้ ไม่ตัด section หรือบรรทัดที่ไม่เกี่ยวข้องออกด้วยการจับคู่ชื่อ tool แบบ heuristic ขอบเขต role ของ Main Agent ต้องมีผลเหนือคำสั่ง direct-execution ที่ขัดแย้งกันใน context ที่ได้รับมา และค่าเริ่มต้นของ CLI/SDK ที่สร้างในตัวต้องไม่ขัดแย้งกับ role ที่ได้รับมอบหมาย

 REQ-019 — (แก้ไขด้วย CHANGE-025, CHANGE-034) `delegate_task`, `delegate_message`, `delegate_message` ต้องคืน control ให้ Main Agent ทันทีพร้อม job id เพื่อ Main ไม่ค้างและรับข้อความใหม่ได้ ระหว่าง worker รัน orchestration ต้องส่ง progress report เข้า Main เป็น continuation turn แบบ hybrid milestone บวก anomaly-gated (milestone tools: bash, anomaly: error สองครั้งติด, backstop: ครบ X tool calls นับจาก report ล่าสุด โดย X จาก config `sub_agent.report_every_tool_calls` ค่าเริ่มต้น 20 และจำกัดไม่เกิน MaxMidJobReports ครั้งต่อ job ค่าเริ่มต้น 3; report เป็น delta เฉพาะ tools ใหม่นับจาก report ล่าสุดพร้อม 1-line status header และตัด result excerpt ที่ 300 runes) ให้ Main ตรวจ scope ว่าขาดหรือเกิน — ถ้าเกิน/ออกนอกขอบเขตให้ `delegate_stop` (blocking) แล้ว `delegate_message` งานใหม่ใน session เดิม; ถ้าตรง scope ให้ตอบสั้นแล้วรอต่อ เมื่อ job ถึง terminal state ต้องส่ง final handoff report เป็น continuation turn เช่นเดิม: `delegate_task`, `delegate_message`, `delegate_message` ต้องรอจน job ถึง terminal state แล้วส่งรายงานครบถ้วนกลับเป็น tool result เดียว (สถานะ, step, worker session, ประวัติ tool ทุกชิ้นพร้อม arguments/รายละเอียดและผลลัพธ์รวม error flag, ข้อความสรุปสุดท้าย) โดยค่าของแต่ละ tool result ในรายงานต้องถูกจำกัดความยาวเพื่อไม่ให้ history บวม — Main Agent ห้ามต้องเรียก tool ใดเพื่ออ่านผลซ้ำ และไม่มี tool สำหรับ polling status/history อีก ผลลัพธ์ต้องถูกส่งให้ Main Agent ตรวจสอบเท่านั้น ห้ามรับหรือเลื่อนแผนต่อโดยอัตโนมัติ Main Agent ต้องอ่านรายงานที่ส่งมาในมือ ตรวจสอบความสำเร็จ และยอมรับ step อย่างชัดเจนผ่าน `delegate_result` พร้อม verification evidence การ review จำกัดอยู่ที่สรุป, ประวัติ tool, validation evidence เท่านั้น ไม่นับ raw file content หรือ large binary payload ที่แนบมากับ report (Main อาจ spot-check ด้วยการอ่านไฟล์เองผ่าน read tools แต่การ accept ยังต้องมี verification evidence ทุกครั้ง) (CHANGE-054) ผลลัพธ์ที่ worker สร้างไฟล์ส่งต่อเป็น file reference พร้อมชื่อ/ชนิด/ขนาดเท่านั้น งานที่ล้มเหลว/หยุด/ไม่สมบูรณ์ retry ต่อใน worker session เดิมผ่าน `delegate_message` ได้ และงานใหม่สั่งต่อเข้า worker session เดิมผ่าน `delegate_message` โดยคงประวัติเดิม (CHANGE-022)

REQ-020 — การ delegation ต้องจอง running job ได้พร้อมกันไม่เกินหนึ่งรายการต่อ parent session โดยครอบคลุม investigation, planned work, follow-up และ continue Job ต้องเก็บ plan revision และ step identity การ completion, retry, continue และ acceptance ต้องตรวจสอบ transition และห้ามเปลี่ยนแผนใหม่ที่เข้ามาแทนที่ History, stop, follow-up, continue และ acceptance ต้องตรวจสอบ ownership ของ parent History ของแต่ละ job ต้องแสดงรายการ tool ที่ worker ใช้พร้อมชื่อ, arguments/รายละเอียด และผลลัพธ์ (รวมสถานะ error) ของแต่ละ tool นอกเหนือจากข้อความสรุปและผลลัพธ์สุดท้าย Continue ต้อง reuse worker session เดิม (workerID/session database เดิม) สำหรับงานใหม่ได้แม้ job ก่อนหน้าจะถูก accept แล้ว โดยต้องไม่มี running job ซ้อนกันและต้องผูกกับ plan step ปัจจุบันหรือเป็น investigation เมื่อแผนเสร็จแล้วต้องยังสามารถทำ investigation หรืองานต่อเนื่องสำหรับงานใหม่ได้โดยไม่ล้างหรือข้ามงานที่กำลังทำอยู่ `delegate_stop` ต้องเป็น blocking call: ยกเลิก job แล้วรอจน terminal state จริง จึงคืนรายงานสุดท้าย (สถานะ stopped + ผลลัพธ์/ความคืบหน้าที่มี) กลับเป็น tool result ห้ามตอบ "ขอหยุดแล้ว" โดยแจ้งผลภายหลัง และการ cancel ของ parent turn ระหว่างรอต้องหยุด worker และคืนรายงานสถานะ stopped (CHANGE-022)

REQ-021 — (แก้ไขด้วย CHANGE-025) Continuation turn ที่ฉีดเข้า parent มีได้สองชนิดเท่านั้น: progress report (ทุก X tool calls) และ final report เมื่อ job จบ (ห้ามมี event ชนิดอื่นเช่น tool started/running); delegation call คืนเฉพาะ ack พร้อม job id; trace ของ worker ยังต้อง display ผ่านเส้นทางเดิมโดยรักษา routing identity (`channel_id` metadata) ของ input ที่เริ่มต้น turn ไว้เหมือนเดิม reservation/revision ของ orchestration เป็นแบบ process-local และการ persist session/cancellation behavior เดิมต้องไม่เปลี่ยน (CHANGE-022)

REQ-022 — Discord ต้องแสดง canonical response text เป็น Markdown ที่อ่านง่าย ไม่ใช่ SDK output ที่ serialize เป็นข้อมูลดิบ Progress ต้องกระชับ และไม่แสดง raw tool arguments/results, delegated task text, reasoning text หรือ internal planning/review chatter แต่ยังคงแสดง operation label ที่ปลอดภัย, ตัวบ่งชี้ความล้มเหลว, เวลา retry, usage และเวลาที่ใช้ได้อย่างมีประโยชน์ การ render ของ transport ต้องอยู่ใน Discord module ข้อความ progress/response ทั้งหมดของ transport ต้อง render แบบ Components V2 (Container + TextDisplay พร้อม `MessageFlagsIsComponentsV2` ทุก send/edit) ห้ามสร้าง embed ใหม่ (CHANGE-022)

REQ-023 — Discord final และ streamed response text ต้องแบ่งหน้าแบบ lossless ที่ขอบเขต Unicode code point ภายในข้อจำกัด message/embed โดยนับ supplementary characters เป็น UTF-16 units อย่างระมัดระวัง ต้องคง whitespace ที่ขอบเขตไว้ และเมื่อมี fenced code block ต้องปิด/เปิด fence สำหรับการแสดงแต่ละหน้าโดยไม่ลบ content ต้นฉบับ Streaming update ต้องแก้ไขหน้าที่มีอยู่ และ terminal response trace ต้องไม่ replay content ที่ถูก stream ไปแล้ว Progress สามารถเป็น summary ที่มีขอบเขตได้ แต่ response text ต้องไม่ถูกตัดทอน

REQ-024 — Discord text/progress transition ต้องส่งต่อ flush failure และเก็บ buffered state ที่ยังไม่ได้ส่งไว้เพื่อ retry แทนการ reset เมื่อส่ง page สำเร็จต้องบันทึกไว้เพื่อไม่ให้ retry ส่งซ้ำ Success/error terminal path ต้องหยุด live footer update, พยายาม flush buffer ที่ค้าง และล้าง retry-status แม้ operation อื่นจะล้มเหลว และต้องแสดง display error ให้ผู้ใช้เห็น โดยยังคงใช้ trace throttling/cooldown เดิม และ reset/close ต้องยกเลิก timer ที่รออยู่ คำสั่ง interaction ที่ต้องทำงานที่ใช้เวลา (สร้าง channel, โหลด model catalogue, บันทึก settings, อ่านรายการ session) ต้อง defer interaction response แบบ ephemeral ก่อนเริ่มงาน แล้วส่งผลลัพธ์หรือข้อผิดพลาดทาง followup เพื่อไม่ให้ interaction หมดอายุภายใน 3 วินาที ข้อยกเว้นคือการเปิด modal ซึ่งต้องตอบทันทีเพราะ Discord ไม่อนุญาตให้เปิด modal ต่อจาก deferred response

REQ-025 — Transport ที่รับไฟล์ (Discord attachment) ต้องดาวน์โหลดไฟล์นั้นแล้วแปลงเป็น file reference ใน file store และแนบ reference ผ่าน `Input.Metadata` โดยไม่เปลี่ยน canonical Turn/ContentPart contract และต้องคง session routing identity กับ metadata เดิมทั้งหมดไว้ รวมถึง `channel_id` ของต้นทาง ข้อความที่มีเฉพาะ attachment ต้องไม่กลายเป็น turn ว่าง — **ยกเลิก/แทนที่: inbound attachment boundary ผ่าน Discord ถูกถอด (CHANGE-059)**

REQ-027 — Discord ต้องมีคำสั่ง `/new` สำหรับสร้าง text channel ใหม่ใน guild เดียวกับช่องที่เรียกคำสั่ง โดยตั้งชื่อช่องจากวันที่และเวลา (รูปแบบ `ai-YYYY-MM-DD-HHMM`) และคัดลอก model settings ของ session ต้นทาง (provider, model, temperature, thinking level, API key pool index) ไปยัง session ของช่องใหม่ทั้งหมด เมื่อสร้างสำเร็จต้องส่งข้อความสรุปการตั้งค่า (provider/model/thinking/temperature/API pool) เข้าไปในช่องใหม่ กรณีเรียกนอก guild, session ต้นทางยังไม่มี model settings หรือสร้างช่องไม่สำเร็จ ต้องตอบกลับแบบ ephemeral ในช่องเดิมโดยไม่สร้าง session ใหม่ พฤติกรรมทั้งหมดอยู่ใน Discord module และห้ามเปลี่ยน core orchestration, persistence หรือ canonical contract

cutover มีเจ้าของเชิงตรรกะเดียว (updater ทำ atomic file ops ส่วน standby re-assert ค่าเดียวกันแบบ idempotent ไม่ใช่ผู้ตัดสินใจคนที่สอง); jobs ที่ยัง running ข้าม restart ต้องคง command/args/session/output ไว้และถูก mark เป็น `interrupted` (retryable) แทน `failed`, intake กลับมา resume จาก live transports บน daemon ใหม่, เขียน handoff file (`update.handoff.json` มี old/new version+hash, old pid, drain flag) เพื่อให้ daemon ใหม่ log resume บน boot แล้วลบ, promote แล้วต้อง verify live intake (live `ai.pid` + live marker ที่ correlate กับ green pid นี้ + live heartbeat fresh) ก่อนจบคำสั่ง (CHANGE-049, CHANGE-053, CHANGE-055, CHANGE-057) — **ยกเลิก/แทนที่: `ai update` blue-green ถูกถอดทั้ง feature (CHANGE-059)**

REQ-044 — Discord gateway ต้องติดตาม liveness ของ websocket (handlers Ready/Disconnect/Resumed บวก last-event timestamp ทุก MessageCreate/InteractionCreate, Connected() รายงาน flag), watchdog goroutine รีเฟรชไฟล์ `discord.heartbeat` ใต้ state root ขณะ connected และ reopen session ด้วย backoff (5 ครั้ง, เริ่ม 1s ทวีคูณ) เมื่อเงียบนานเกิน 3 นาทีหรือ flag หลุด; `discord.heartbeat` เก็บไว้เป็น operator-visible liveness signal (ไฟล์ยังไม่มีก่อน Ready ครั้งแรกไม่นับว่าล้มเหลว); automated repair จบที่ in-process watchdog reopen — ไม่มี supervisor ภายนอก: daemon ตายหรือ gateway กู้ไม่ขึ้นต้อง `ai start` เอง (tradeoff ที่ยอมรับใน CHANGE-055); ไม่แตะ V2 display, OS tools, หรือ update path (CHANGE-050, CHANGE-055) — **ยกเลิก/แทนที่: Discord gateway liveness/heartbeat ถูกถอด (CHANGE-059)**

REQ-045 — Dual loop-control: system caps บวก prompt discipline พร้อม checklist, tool budgets และ failure lessons — ระบบบังคับ hard caps ในโค้ดสำหรับ worker loop: max tool calls ต่อ turn attempt, max consecutive read probes (`read` ติดกันโดยไม่มี progress tool คั่น — CHANGE-087 เหลือ probe tool เดียว), max bash output size ต่อ result; เมื่อเกินต้อง auto-fail ทันทีด้วย error ที่ชัดเจนและห้าม retry ซ้ำ (budget failure เป็น fatal); คงพฤติกรรมเดิมทั้งหมดเมื่ออยู่ใต้ limits (turn ปกติที่ใช้ single-digit calls ไม่เปลี่ยน) — ส่วน prompt discipline: checklist ตามลำดับต่อ task ใน `requirements/loop-control.md`, ทุก delegation ต้องประกาศ tool budget (max reads/edits/bash), stop condition เมื่อ budget เกิน = fail แล้วเขียน lesson ลง `requirements/lessons.md` แทนการวนซ้ำ; Main ใช้ `read` เองภายใต้ budget (อ่าน `index.md` ก่อนเสมอ แล้วอ่านเฉพาะไฟล์ที่ index.md ระบุ — ดู planner self-read ใน requirements/loop-control.md) (CHANGE-054); planner/worker prompts อ้างอิง checklist นี้; ไม่แตะ transport/discord display, gateway liveness, keepalive, update path (CHANGE-052) — **ยกเลิก/แทนที่: loop-control ยังใช้; เฉพาะส่วน Discord-display ถูกถอด (CHANGE-059)**

REQ-046 — Mobile transport + stateless runtime state (CHANGE-058): (1) `transport/mobile` เป็น WebSocket input source/display ฝั่ง daemon ที่พูด JSON ตรงกับ `sdk.Input`/`sdk.Output` และวางผ่าน `sdk.MergeInputSources` + `sdk.DispatchDisplay` เหมือน transport อื่น โดยไม่แตะ core loop; (2) การเข้าถึง mobile ใช้ 2 ขั้น: hostname ของ Cloudflare quick tunnel (สุ่ม ยังไม่ publish อะไร) + header `Authorization: Bearer <Cloudflare API token>` ตรวจกับ `GET /user/tokens/verify` ก่อน upgrade และเก็บ token ที่ผ่านไว้ใน RAM — การเชื่อมต่อครั้งถัดไปที่ใช้ token เดิมผ่านทันทีโดยไม่ต้องยิง Cloudflare ซ้ำ (token ผิดยังโดน 401 + lockout เหมือนเดิม, และ handshake ที่ถูกปฏิเสธต้องถูก log เป็น address + เหตุผลโดยไม่เขียน token) — header ขาด/ผิดรูปแบบ = `401` และไม่นับ, token ผิด 5 ครั้ง = `429` ล็อก address นั้น 30 วิ แล้ว 60/120/240/300 วิ (เพดาน) โดยนับตาม `CF-Connecting-IP` → `X-Forwarded-For` → peer (หลัง tunnel peer เป็น cloudflared local เสมอ) และห้ามใช้ token เป็นส่วนของ key (หมุน token หลุดล็อกได้), success รีเป็น 0, Cloudflare ติดต่อไม่ได้ = `503` ไม่นับ (fail closed); (3) daemon ไม่มี credential ของตัวเอง — เมื่อ handshake ผ่านจึงเก็บ Cloudflare token ใน memory เท่านั้น (restart หาย แล้วรอมือถือส่งใหม่) และใช้ token นั้นยิง Cloudflare API ต่อ; account id และ database id ต้องถูกหาจาก token เอง (`GET /accounts` → `GET /accounts/{id}/d1/database`) ไม่ต้องตั้งค่า id ใน `config/entry.json`; (4) `runtime/d1store` ทำ D1 เป็นต้นทางของ runtime state: `config/provider|system` (CHANGE-087 ตัด `config:attachment` และ `config:browser` ออก) (ไม่รวม `config/entry.json` เพราะเป็น bootstrap ของ gateway ที่ต้องอ่านก่อนถึง D1 ได้) และไฟล์ session DB ถูก materialize ลง `config/*.json` + `data/sessions/*.db` ตอน handshake แรกของ connection ใหม่ (local files ยังเป็นรูปแบบที่ loader/saver เดิมใช้ จึงไม่เปลี่ยน CON-001/CON-002) และถูก push กลับหลังเปลี่ยน (ขนาดเกิน limit ของ D1 = ข้ามพร้อม log ไม่ล้มทั้ง runtime); (5) ทุก turn ที่จบถูกเขียนเข้า D1 ผ่าน `POST /accounts/{a}/d1/database/{d}/query` ตามลำดับ FIFO เพื่อให้ประวัติบนมือถือเรียงตาม `seq`; หลัง hydrate config สำเร็จ daemon ต้อง reload provider (adapters/router) จาก config ที่เพิ่งถูกดึง และ `transport/mobile` ต้องแสดงคำตอบของ turn ที่ถูก trace โดยอ่าน text จาก `TraceResponseContent` ปิด turn ที่ `TraceResponse` (turn ที่ trace แล้วไม่มี final `output.Content`) — user turn ที่รับเข้าต้องถูกเขียนลง D1 ด้วย ไม่ใช่เฉพาะ model turn; session ที่ materialize มาจาก D1 ต้องถูกย้ายไปใช้ provider ที่ daemon มีอยู่จริงหลัง reload (ถ้า provider เดิมไม่มีแล้ว) ไม่เช่นนั้นทุก turn ของแชทเก่าจะล้มด้วย `sdk: provider is required`; (6) ไม่เพิ่ม credential ใหม่ (ไม่มี node token, ไม่มี state encryption key) — config/provider ที่เก็บใน D1 อ่านได้ด้วย Cloudflare token เดียว (single-operator tradeoff, CON-012); daemon ต้องเสิร์จ `/api/sessions*`, `/api/turns*`, `/api/models`, `/api/node`, `/api/ping` เองจาก D1 ผ่าน tunnel และต้อง stream ทุก turn: frame `delta` ต่อชิ้นข้อความ, `trace` สำหรับความคืบหน้า/เครื่องมือ, `message` เฉพาะตอนที่คำตอบไม่ได้มาเป็น delta และ `done` ปิด turn; มือถือเลือก provider/model ต่อแชทได้ (`GET /api/models` + `PATCH /api/sessions/:id`) โดย daemon ตรวจกับ router, ใส่ให้ session ที่เปิดอยู่ และเก็บลง D1 เพื่อให้ค่าอยู่ข้ามการรีสตาร์ต; adapter ต้องเลือก streaming dialect ตาม endpoint (gateway แบบ OpenAI-compatible ใช้ `/chat/completions`) และ D1 ต้องได้หนึ่ง turn ต่อหนึ่ง turn บนสาย เพื่อให้แอปใช้ที่อยู่เดียว และ `/api/state` ต้องไม่ถูกเสิร์จเด็ดขาด (กัน provider keys หลุดออกทาง tunnel)

REQ-047 — Daemon มี gateway เดียว: `transport/mobile` ผ่าน Cloudflare quick tunnel (CHANGE-059) — `ai` เป็น daemon สำหรับ AIxodia เท่านั้น ไม่มี CLI transport, ไม่มี Discord transport, ไม่มีคำสั่ง `ai update`/`uninstall`/`stop`/`discord`/`browser`/`system`/`cli`/`provider` และไม่มี self-update/blue-green/pid-handoff; จุดเข้าถึงเดียวคือ WebSocket บน tunnel URL ที่หาได้จาก `GET /api/node` ที่ daemon เสิร์จเอง หรืออ่านแถว `nodes` ใน D1 ที่ daemon เขียน heartbeat เอง (CHANGE-082) และต้องผ่าน handshake 2 ขั้นตาม REQ-046; runtime config/session state อยู่ที่ Cloudflare D1 (REQ-046) จึงไม่มีคำสั่งจัดการ config แบบ local — การตั้ง provider/model/system prompt ทำผ่าน D1 (`/api/state/...`) ไม่ใช่คำสั่งใน binary; process เดียวรับ `daemon` (หรือรันเปล่า) แล้วทำงานจนถูก signal

REQ-048 — มือถือเป็นเจ้าของ provider, key pool และโมเดลของแต่ละ agent (CHANGE-066): (1) `transport/mobile/admin.go` เสิร์จผ่าน tunnel (หลังผ่าน gate ตาม REQ-046) เฉพาะ `GET|POST /api/providers`, `POST /api/providers/{id}/keys` (add/remove/replace), `DELETE /api/providers/{id}`, `POST /api/providers/refresh` และ `GET|PUT /api/settings`; provider ใหม่ต้องผ่าน router validation ก่อนถูกยอมรับ และการ probe ของ `refresh` ต้องยิงจริง 1 token เพื่อให้เห็นเหตุผลจริง (เช่น 401 key ตาย, 403 free tier) ไม่ใช่แค่ 200 จากการบันทึก; (2) key เป็น write-only — ไม่มีเส้นทางไหนส่งค่า key กลับออก tunnel (รวมทั้ง error message), ตอบกลับเป็นจำนวน key + ข้อความสถานะ/เหตุผลเท่านั้น; (3) การเขียน provider/settings ต้องเขียน `config/provider` + `config/system` ทั้งไฟล์และ D1 (REQ-046(4)) แล้ว reload runtime ทันที เพื่อให้ค่าของมือถืออยู่ข้าม restart โดยไม่ต้องแก้ไฟล์บนเครื่อง; (4) `PUT /api/settings` ตั้ง main/sub route (provider + model) ของ agent แต่ละตัวโดยตรวจกับ router และใช้แทนค่า boot; (5) มือถือหยุด turn ได้: เฟรม `cancel` ให้ daemon ยกเลิก context ของ turn ที่กำลังวิ่งใน session นั้นทันที (provider request + tool call) แล้วตอบ `done` stage `cancelled`; ถ้าไม่มี turn วิ่งอยู่ตอบ `done` stage `already_done` (ไม่ใช่ error) และ trace ที่ถูกยกเลิกต้องกลายเป็น `done/cancelled` ไม่ใช่ provider error; (6) turn ที่ล้มต้องรายงานกลับมือถือผ่านเฟรม `error` (ข้อความสั้น) เพื่อให้เห็นเหตุผลจริง เช่น `Invalid API key` หรือ `FreeTierError` แทนการ retry เงียบ ๆ; (7) สถานะ provider เป็นสามค่า: provider ที่ยังไม่เคย probe ต้องรายงาน `probed=false` และ `reachable` ที่ยังไม่รู้ห้ามถูกนับเป็น "ใช้ได้" — การแก้ key pool ของ provider ต้องล้างผล probe เดิมเพื่อให้รายงานว่ายังไม่ทดสอบอีกครั้ง; (8) ต้องทดสอบ provider เดี่ยวได้โดยไม่ต้องรอทั้งรายการ (`POST /api/providers/{id}/refresh` → `ProviderStatus`) เพราะผู้ใช้ที่กำลังแก้ key ที่ตายต้องการคำตอบของตัวนั้นก่อน; (9) การ probe ต้องเริ่มจากโมเดลที่ตอบได้ล่าสุดของ provider นั้นก่อน (`ProviderStatus.WorkingModel`, ใช้เป็น `default_model` ของ `/api/models` ด้วย) เพราะโมเดลแรกในแคตตาล็อกไม่ใช่หลักฐานอะไรเกี่ยวกับ provider, และคำตอบที่ provider จะพูดซ้ำ (401, 403, 429) ต้องหยุดการเดินหาโมเดลถัดไปทันทีพร้อมข้อความที่บอกว่าเป็นการปฏิเสธ/โควตาหมด — turn ที่เจอคำตอบแบบนั้นต้องรายงานเดี๋ยวนั้น ไม่ retry (OpenCode Zen ตอบ free tier ที่มาจากนอก client ของมันด้วย 403 FreeTierError และนับทุกคำขอที่ถูกปฏิเสธไปกินโควตาของตัวเอง); (10) `POST /api/providers/refresh` ต้องตอบภายในเวลาที่มือถือและ tunnel ยอมรอ: ตรวจทีละ provider ไม่เกิน 4 ตัวพร้อมกัน และแต่ละตัวมีงบเวลา (25 วินาที ครอบทั้ง discovery และ probe) — gateway ที่ค้างหนึ่งตัวต้องไม่ทำให้ทั้งรายการหายเกินเวลาแล้วถูกมือถือตัดทิ้ง;
